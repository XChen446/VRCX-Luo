# 引擎迁移指南（SQLite → MySQL / PostgreSQL）

> 面向**用户与维护者**的操作指南：把 VRCX-K 的 SQLite 数据搬迁到 MySQL/MariaDB 或 PostgreSQL，以及反向备份。机制说明见 §4；实现细节见 `PGSQL_DESIGN.md` §6.2（搬迁管道设计）与 `pushEngine.js`/`pullEngine.js` 源码。

---

## 1. 适用场景与前置认知

| 场景 | 是否支持 |
|------|---------|
| SQLite → PostgreSQL（默认库名 `vrcx`） | ✅ 支持（UI「迁移」按钮） |
| SQLite → MySQL 8.0+ / MariaDB 11.x | ✅ 支持（同上） |
| 远程 → SQLite（备份/回退） | ✅ 支持（UI「备份」按钮，`pullToSqlite`） |
| MySQL ↔ PostgreSQL 直接互迁 | ❌ 不支持（管道是 SQLite 源/目标，先迁到 SQLite 再迁出） |

**三个重要事实**：

1. **引擎切换需要重启应用**。C# 侧连接池（`SQLite.Instance` / `PostgreSQL.Instance` / `MySQL.Instance`）在**启动时**初始化；运行中切换配置不会重建池。UI 的「迁移数据并切换」只保存配置 + 执行搬迁，**不会自动重启**——重启由用户完成。
2. **搬迁目标是当前运行的单例**。`pushFromSqlite` 把数据推入**已初始化**的引擎单例；UI 守卫 `canPushToRemote` 会比较表单值与启动时配置快照（`bootDbConfig`），不一致时禁用迁移按钮（防止表单与运行池不一致时把数据推到错误主机）。
3. **数据完整性优先**：搬迁失败不会丢源数据（源 SQLite 文件只读）；目标引擎按"组"收集错误，单组失败不中断其余组。

## 2. 前置条件

### 2.1 服务端准备

**PostgreSQL 16 或 17**（推荐；15+ 亦可）：

```sql
-- 以超级用户执行一次(或由 DBA 预授权):
CREATE USER vrcx WITH PASSWORD 'vrcx';
CREATE DATABASE vrcx OWNER vrcx;
-- 注意:VRCX 需要 CREATE SCHEMA 权限(每个账号一个 schema)
GRANT ALL ON SCHEMA public TO vrcx;
```

**MySQL 8.0+ / MariaDB 11.x**：

```sql
CREATE DATABASE vrcx CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'vrcx'@'%' IDENTIFIED BY 'vrcx';
GRANT ALL PRIVILEGES ON vrcx.* TO 'vrcx'@'%';
FLUSH PRIVILEGES;
```

**本地开发一行启动**：

```bash
# PostgreSQL
docker run -d --name vrcx-pg -e POSTGRES_PASSWORD=vrcx -e POSTGRES_USER=vrcx -e POSTGRES_DB=vrcx -p 5432:5432 postgres:16
pg_isready -h localhost -p 5432 -U vrcx

# MySQL
docker run -d --name vrcx-mysql -e MYSQL_ROOT_PASSWORD=vrcx -e MYSQL_DATABASE=vrcx -e MYSQL_USER=vrcx -e MYSQL_PASSWORD=vrcx -p 3306:3306 mysql:8.4
```

### 2.2 VRCX 侧

- 退出 VRCX（避免搬迁期间写入，源文件被独占锁定风险）
- 记录当前 SQLite 库位置：设置页「高级」会显示当前路径（`VRCX_Database.name`，sqlite 模式下即文件路径）；未配置时默认落在 C# `Program.ConfigLocation`（AppData 目录）——详见 `CONFIG_REFACTOR.md`

## 3. 操作步骤（UI 路径）

入口：**设置 → 高级 → 数据库引擎**（`AdvancedTab.vue` 的 SettingsGroup）。

### 3.1 迁移到远程引擎

1. **选择引擎**：引擎模式 `Select` 选 `postgresql` 或 `mysql`。
2. **填写连接字段**：host / port / username / password / name（库名）。
3. **测试连接**：点击「测试连接」——成功显示绿色 ✓；失败显示原因（网络、权限、库不存在等）。
4. **迁移数据并切换**：点击「迁移」→ 对话框中选择**源 SQLite 文件**（预填当前库路径）→ 确认。进度复用 `DatabaseUpgradeDialog` 展示。
   - 迁移按钮被禁用时，悬停查看 `canPushToRemote` 守卫消息（通常是"表单与当前运行配置不一致，请先重启"）。
5. **重启应用**：VRCX 以新引擎启动。首次启动会自动：
   - `initGlobalSchema()` 建 18 张全局表（PG 在 `public` schema）
   - 迁移运行器执行：v16 等 `after: "sqlite"` 锁定的 .map 自动跳过，checkpoint 记录最新版本
   - 首个账号登录时 `initUserSchema(prefix)` 建 `account_{prefix}` schema + 22 张用户表
6. **验证**：登录后检查好友/通知/游戏日志数据完整；设置页 StatusBar 的数据库池监控显示引擎与连接状态。

### 3.2 备份 / 回退到 SQLite

1. 引擎模式选 `sqlite`，填写 SQLite 文件路径。
2. 点击「备份」（`pullToSqlite`）——远程库全部数据（18 全局 + 22 用户白名单 + mirror 兜底）写入目标 SQLite 文件。
3. 重启应用，以 SQLite 模式运行。

> 远程 → SQLite 路径是**备份/回退**语义：目标 SQLite 文件由管道重建表并拷贝数据。引擎切换回 SQLite 后如数据异常，可回到远程库确认数据仍在（远程库未被清除）。

## 4. 搬迁机制说明

### 4.1 push 流程（`pushFromSqlite(srcConnStr, options)`）

```
§1  连接源 SQLite(只读)
§2  initGlobalSchema() + initUserSchema(每个 prefix)——目标引擎建表(类型映射后 DDL)
§3  全局表 18 张白名单(GLOBAL_TABLES,含 configs):逐表分页 select → bulkInsert('ignore')
§4  用户表 22 张白名单(USER_TABLE_NAMES):按 prefix 逐表分页 → userTable(prefix, name) 定位目标
§5  行数严格校验:count(dst) == count(src) 每表
§6  mirror 兜底:白名单外发现的任何表(上游新增/遗留)经 PRAGMA table_xinfo 读列结构
    → createTable(引擎类型映射) → 分页拷贝;UNIQUE/索引不重建,仅列级约束(单列 PK 内联,
    复合 PK 表级子句);每张 warn 日志标注
§7  分组事务:每"组"(全局 / 每个 prefix / mirror)一个事务(原子 + 每组一次 fsync)
    单组失败收集错误继续,不中断整体
```

关键语义：
- **`bulkInsert('ignore')`**：目标已存在行（如 configs 表的 `schema_version`）不被覆盖——`runMigrations` 在搬迁前已写入版本 checkpoint，push 不会污染启动状态。
- **`activity_sessions_v2` 的 `session_id`**：PG 表用 `GENERATED BY DEFAULT AS IDENTITY`，显式复制原值被接受（`GENERATED ALWAYS` 会拒绝——类型映射已统一 BY DEFAULT）。
- **分批**：默认 500 行/批，规避 PG 参数上限（65535）。
- **自增 id 原样复制**：`SELECT *` 包含 id 列，bulkInsert 原样写入。

### 4.2 pull 流程（`pullToSqlite(dstConnStr, options)`）

与 push 对称：远程引擎为源（经当前单例 adapter），SQLite 文件为目标。同样走白名单 + mirror 兜底 + 分组事务 + 行数校验。

### 4.3 引擎差异对照（搬迁后的行为变化）

| 维度 | SQLite | PostgreSQL | MySQL |
|------|--------|-----------|-------|
| 表名形态 | `prefix_name`（平铺） | `account_prefix.name`（schema 隔离） | `prefix_name`（平铺） |
| 整数主键 | INTEGER PRIMARY KEY | BIGINT IDENTITY | BIGINT AUTO_INCREMENT |
| 事务隔离 | Serializable | Read Committed（默认） | REPEATABLE READ（InnoDB 默认） |
| 大小写 | 不折叠 | 未加引号标识符折叠小写 | 表名大小写敏感（Windows 下不敏感） |
| LIKE 通配 | `_` 单字符 | 同（需 ESCAPE 转义） | 同 |
| 外部进程写库 | 不推荐 | 不推荐（trigger+NOTIFY 可覆盖） | 不推荐（计数器轮询兜底） |

对普通用户影响很小：VRCX 表名/列名均小写蛇形、单进程模型，以上差异已在适配器层处理。

## 5. 故障排查

| 现象 | 原因与处理 |
|------|-----------|
| 迁移按钮禁用，title 有守卫消息 | 表单与启动时配置不一致——保存后重启应用再操作 |
| 测试连接失败 | 网络不通 / 端口错误 / 用户无权限 / 库不存在——按 §2.1 检查服务端 |
| 搬迁中某组失败（日志 ✗） | 该组错误已收集，整体继续；修复后重试（操作幂等，已搬迁的表 `'ignore'` 不重复） |
| 迁移后登录无数据 | 源文件选错（选了空库）——检查 §3.1 步骤 4 的源路径；源 SQLite 未受影响 |
| PG 首次启动报 schema 相关错误 | vrcx 用户缺 CREATE SCHEMA 权限——§2.1 GRANT |
| 行数校验失败 | 目标表有外部写入或源在搬迁中变动——退出 VRCX 后重试 |
| 数据乱码 | MySQL 连接字符集问题——确认库为 utf8mb4（§2.1） |

## 6. 已知限制（有意设计）

- **无 MySQL ↔ PG 直迁**：管道只支持 SQLite 源/目标（先迁 SQLite 再迁出）。
- **删除用户数据流程不存在**：`dropUserSchema`（PG 清理账号 schema）方法已实现但未接入 UI——DB 数据永久保留是有意设计（重新登录可恢复），未来"彻底删除账号"功能待产品决策。
- **密码明文存储**：`VRCX_Database.password` 存于 `VRCX.json`（连接配置的安全存储属 Issue #5 范围，未实现）。
- **单进程模型**：外部进程写库非支持场景（完备层计数器轮询可兜底检测）。
- **切换引擎后旧 SQLite 文件保留**：不自动删除，可随时备份。
